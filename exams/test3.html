  • +0.25(a) Sinks indices 2, 1, 0 (n/2 - 1 = 2)
  • +0.5(a) After index 2: [3, 9, 8, 7, 5, 2, 1]; index 1 changes nothing (9 ≥ 7, 5)
  • +0.5(a) After index 0: [9, 7, 8, 3, 5, 2, 1] (3 sinks past 9, then past 7)

  i=2: 2 vs children 8, 1 → swap with 8   [3, 9, 8, 7, 5, 2, 1]
  i=1: 9 vs children 7, 5 → stays          [3, 9, 8, 7, 5, 2, 1]
  i=0: 3 vs 9, 8 → swap with 9             [9, 3, 8, 7, 5, 2, 1]

round 1: swap 9 ↔ 1 → [1, 7, 8, 3, 5, 2 | 9], sink 1 in size 6
         1 vs 7, 8 → 8; then 1 vs 2 → 2    [8, 7, 2, 3, 5, 1 | 9]
round 2: swap 8 ↔ 1 → [1, 7, 2, 3, 5 | 8, 9], sink 1 in size 5
         1 vs 7, 2 → 7; then 1 vs 3, 5 → 5 [7, 5, 2, 3, 1 | 8, 9]

Rubric and reference solution

3 pts. Start from 0 and add each item the answer earns; penalties come off at the end.

  • +0.5(a) null: the default hashCode is based on object identity, so the two equal points almost certainly land in different buckets and get never calls equals on the stored one
  • +0.5(b) Equal objects must have equal hash codes (override hashCode whenever you override equals)
  • +0.75(c) Combines both fields, e.g. 31 * x + y or Objects.hash(x, y), using only the fields equals uses
  • +0.75(d) Correct (equal points get equal codes) but every key collides into one bucket: get becomes O(n)
  • +0.5(e) e.g. (1, 2) and (2, 1). Still correct: collisions only cost time, because equals decides matches

@Override
public int hashCode() {

}

The contract only goes one way: a.equals(b) ⇒ a.hashCode() == b.hashCode(). Unequal objects may share a code; that is a collision, which the map handles with equals. A constant hashCode keeps the rule but turns the table into one long chain.

  • +0.25Both throw IllegalArgumentException for a null key
  • +0.5Both start at indexFor(key)
  • +0.75Both loop until an empty (null) slot, not until the first tombstone
  • +0.75Both skip tombstones when matching: !slots[i].deleted && slots[i].key.equals(key)
  • +0.5Both step with i = (i + 1) % slots.length
  • +0.5get returns the value on a match, null after the loop
  • +0.75remove marks the entry deleted = true (doesn't set the slot to null)
  • +0.5remove decrements size and leaves used unchanged
  • +0.5remove returns the old value, or null if not found
  • −1remove sets the slot to null, breaking the search for keys further along
  • −0.5Stops searching at a tombstone

public V get(K key) {
  if (key == null) throw new IllegalArgumentException();
  int i = indexFor(key);
  while (slots[i] != null) {                       // only an empty slot ends the search
    if (!slots[i].deleted && slots[i].key.equals(key)) return slots[i].value;
    i = (i + 1) % slots.length;                    // tombstone or other key: keep going
  }
  return null;
}

public V remove(K key) {
  if (key == null) throw new IllegalArgumentException();
  int i = indexFor(key);
  while (slots[i] != null) {
    if (!slots[i].deleted && slots[i].key.equals(key)) {
      V old = slots[i].value;
      slots[i].deleted = true;                     // tombstone, NOT null: keeps later probe paths intact
      size--;                                      // used stays the same: the slot is still taken
      return old;
    }
    i = (i + 1) % slots.length;
  }
  return null;
}

used counts slots that aren't null. A tombstone is still not null, so removing a key changes size but not used. Only a rehash clears tombstones.

public V remove(K key) {
  if (key == null) throw new IllegalArgumentException();
  int i = indexFor(key);
  Node<K, V> prev = null, curr = buckets[i];
  while (curr != null && !curr.key.equals(key)) {   // walk with a trailing pointer
    prev = curr;
    curr = curr.next;
  }
  if (curr == null) return null;                    // not in this chain
  if (prev == null) buckets[i] = curr.next;         // removing the head
  else prev.next = curr.next;                       // removing from the middle or end
  size--;
  return curr.value;
}

  • +0.25Saves heap[0] to return

  • +0.25Calls sink(0) and returns the saved value
  • +0.5sink loops while i has a left child: 2 * i + 1 < size
  • +0.75Picks the smaller child, checking 2 * i + 2 < size before using the right one

  • +0.75Continues from the child's index (i = c)
  • −0.5Compares with </> on objects instead of compareTo

public T remove() {
  if (size == 0) throw new NoSuchElementException();
  T best = heap[0];
  heap[0] = heap[size - 1];        // last value moves to the root
  heap[size - 1] = null;           // no stale reference
  size--;
  sink(0);
  return best;
}

private void sink(int i) {
  while (2 * i + 1 < size) {                         // i has at least a left child
    int c = 2 * i + 1;
    if (c + 1 < size && heap[c + 1].compareTo(heap[c]) < 0) c++;   // the smaller child
    if (heap[i].compareTo(heap[c]) <= 0) break;      // already in order
    swap(i, c);
    i = c;
  }
}

  • +0.5Looks up the index with where.get(item)
  • +0.25Throws IllegalArgumentException when it isn't there
  • +0.75Swaps the item's slot with the last slot (size - 1)
  • +0.75Removes the item from where
  • +0.5Nulls the old last slot and decrements size
  • +0.75Skips the fix-up when the removed item was in the last slot
  • +1Restores order at index i with both swim(i) and sink(i) (the moved entry may need to go either way)
  • +0.5Uses the GIVEN swap so the moved entry's map index is updated
  • −0.5Only sinks (or only swims) after the move
  • −0.5Searches the array for the item instead of using the map (O(n))
  • −0.25Leaves the removed item in where
  • −0.125Minor logic or major syntax errors showing lack of understanding
public void remove(T item) {
  Integer i = where.get(item);
  if (i == null) throw new IllegalArgumentException();
  int last = size - 1;
  swap(i, last);                 // item goes to the end; the last entry fills its slot
  where.remove(item);            // forget the removed item
  heap[last] = null;
  size--;
  if (i < size) {                // unless we removed the last slot itself,
    swim(i);                     // the moved entry may be smaller than its new parent
    sink(i);                     // or larger than its new children
  }
}

Unlike removeMin, the hole can be anywhere, so the last entry that fills it may be smaller than its new parent (needs swim) or larger than its new children (needs sink). Calling both is safe: at most one of them moves anything.

Rubric and reference solution

5 pts. Start from 0 and add each item the answer earns; penalties come off at the end.

  • +0.25Throws IllegalArgumentException for null or negative k
  • +1Uses a min-heap (the default PriorityQueue): its root is the smallest of the current top k
  • +0.75Adds freely while it holds fewer than k values
  • +1Once full, adds x only if x > peek(), removing the root first
  • +0.75Never holds more than k values
  • +0.5Handles k = 0 without crashing
  • +0.75Empties the queue into a list and reverses it, so the largest is first
  • −1Puts all n values into the queue (O(n log n) time, O(n) space)
  • −0.5Uses a max-heap of size k, which throws away the largest values instead of the smallest
  • −0.5Sorts the whole array
  • −0.125Minor logic or major syntax errors showing lack of understanding
public static List<Integer> topK(int[] a, int k) {
  if (a == null || k < 0) throw new IllegalArgumentException();
  PriorityQueue<Integer> pq = new PriorityQueue<>();   // MIN-heap of the k largest seen so far
  for (int x : a) {
    if (pq.size() < k) {
      pq.add(x);
    } else if (k > 0 && x > pq.peek()) {   // beats the smallest of the current top k
      pq.remove();
      pq.add(x);
    }
  }
  List<Integer> out = new ArrayList<>();
  while (!pq.isEmpty()) out.add(pq.remove());   // comes out smallest first
  Collections.reverse(out);                     // largest first
  return out;
}

The counter-intuitive part: to keep the largest k you use a min-heap, because the value you may need to throw out next is the smallest of the ones you're keeping. Each of the n values costs at most one O(log k) remove and add.
